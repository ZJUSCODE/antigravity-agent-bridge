# 双 AI 对等协商与交叉审查协议规范（Peer Exchange Protocols）

本手册定义 **Antigravity** 与 **OpenAI Codex** 之间进行多轮工程对话时的标准协作模式、证据准则、收敛状态机与向用户交付结论的汇总模板。

---

## 一、四大标准协议（`--protocol`）

### 1. `rfc` — 架构方案碰撞与定稿（Architecture Trade-off Debate）
- **适用场景**：新功能技术选型、数据结构/接口契约设计、重构路线评估、跨模块边界划分。
- **执行要求**：
  - **Round 1（立论与质询）**：发起方给出背景约束、候选方案与核心权衡点；被调用方独立寻找隐含假设漏洞、并发/故障边界或更简替代实现，禁止空泛附和。
  - **Round 2（反驳或收敛）**：发起方逐条吸收有效反例并修订契约，对不采纳的建议给出明确技术依据；双方确认最终接口、数据流与风险边界。
- **收敛标记**：回复末尾带 `[PEER_STATUS: CONVERGED]`（达成共识）或 `[PEER_STATUS: NEEDS_ROUND]`（仍有实质分歧）。

### 2. `review` — 对抗式交叉代码审查（Adversarial Cross Code Review）
- **适用场景**：代码编写完成后的互审、PR/Git Diff 检视、高风险改动上线前把关。
- **分级准则**：
  - `[P0]`：数据损坏/丢失、权限绕过/注入漏洞、必现崩溃或死锁（阻断级，必须修复后复审）。
  - `[P1]`：功能逻辑错误、并发竞态、未处理异常分支、资源句柄泄漏（高优必改）。
  - `[P2]`：极端输入边界、明显性能退化或兼容性隐患（建议本轮处理）。
  - `[P3]`：命名或局部可读性建议（非阻断，一句话带过，禁止刷屏）。
- **证据红线**：每条缺陷必须标注准确的 `文件路径:行号`（或符号名）与触发路径；配合 `--diff-git` 自动附带工作区真实变更。无实质问题时直说“未发现 P0-P2 缺陷”。
- **裁决标记**：`[PEER_VERDICT: PASS]` 或 `[PEER_VERDICT: CHANGES_REQUIRED]`。

### 3. `debug` — 双盲根因假设排障（Root-Cause Hypothesis Tournament）
- **适用场景**：偶发竞态、跨进程/编码/环境黑盒故障、单方连续排障受阻。
- **执行要求**：
  - 严格拆分 **已观测事实（Observed Facts）** 与 **待证伪假设（Hypotheses）**。
  - 双方各自给出独立根因排序，并共同选出**单步验证成本最低、区分度最高**的诊断命令或日志探针，验证后再动手改代码。

### 4. `audit` — 洁净室独立验收审计（Clean-Room Verification Audit）
- **适用场景**：主代理完成复杂实现后，请对方在不看作者主观辩解的前提下，直接对照「用户原始需求 + 真实代码 Diff + 测试结果」做独立验收。
- **核查重点**：是否只过了语法检查而未真正走通业务链路、是否有遗漏边界或误伤无关文件。

## 二、收敛状态机与防乒乓死循环守则

1. **预算上限**：
   - 默认往返 **2 轮**；若第 2 轮仍返回 `NEEDS_ROUND` 或 `CHANGES_REQUIRED`，最多追加至 **3～4 轮**。
   - 若第 4 轮仍存在路线分歧，立即停止拉锯，将双方核心依据整理为清晰的「二选一决策矩阵」交由用户拍板。
2. **硬件级防递归锁（`AGY_CODEX_PEER_CALL=1`）**：
   - 桥接脚本在拉起对方 CLI 时会自动注入环境变量 `AGY_CODEX_PEER_CALL=1`。
   - 任何处于被调用回合的 Agent **严禁**再次调用同侪桥接脚本，必须直接基于代码和事实给出独立答复。
3. **只读安全默认**：
   - `rfc`、`review`、`audit` 阶段默认以只读权限运行，不擅自改写工作区未提交代码；需要主代理改码修复 `P0/P1` 后，再发起下一轮复审。

---

## 三、向用户汇报的最终收敛格式（精炼高信噪比）

多轮协商结束后，向用户呈现结构化结论（避免复读中间客套过程）：

1. **最终共识结论 / 审定结果**（直接给出定稿方案或 `PASS` / 修复闭环状态）
2. **双 AI 关键碰撞收获**（列出通过互审发现并修正的真实隐患、推翻的错误假设或关键权衡，附文件链接）
3. **未决分歧（仅在确需用户决策时保留）**
